# 待澄清任务控制与修订

2026-10-11 补充。普通 Chat 与项目助手等待问题答案时保留输入框，明确控制由服务端处理。支持以下入口：

| 输入 | 行为 |
| --- | --- |
| 取消当前任务／取消刚才的任务 | 结束原任务，保留已完成结果；不请求模型 |
| 修改需求：只讨论方案，不执行 | 同一任务采用新要求，重新校验授权与目标 |
| 修改需求 | 保留原任务与材料，等待下一条真实新要求；不请求模型 |
| 换个话题：TCP 握手是什么？ | 结束原任务，再以新正文开始新任务 |
| 换个话题 | 结束原任务，等待新消息；不请求模型 |

也支持相应明确英文命令。简短回答、否定、引用、假设和含混控制不会静默修改任务，例如“改成蓝色”“不要取消任务”“如果取消会怎样”。系统提示用户在问题卡中回答，或使用明确任务控制。没有待答任务时仍走普通 Chat。执行中继续使用停止入口；本次没有任意执行步骤的暂停检查点或运行中插话。

修改需求沿用 `task_id`、累计调用上限、已完成操作及未知结果账本。旧 `Q_*` 确认与旧目标选择失效，当前版本、工具及新要求重新校验；新要求可以明确执行，也可以明确只讨论。未使用的收费次数授权由新要求替换，不因反复修改而累加。已有成功操作按原业务键复用，未知结果继续核对，不自动重发。

带正文的修订、分两条消息修订及问题卡“修改需求”都保留原素材引用；分两条提交时，新上传素材或显式新上下文优先。原生压缩后的修订沿可信会话 lineage 复用原任务与预算，并冻结操作提交时的归属。素材与项目仍需满足当前会话的归属校验；压缩前附件不再可读时明确提示重新上传，任务保留在修订状态，输入草稿不清空。

纯控制将真实用户输入与确定性回执追加到 Hermes 原生历史，标记已持久化，后续模型轮次和停服保存不会重复插入。保存回执失败时，控制状态仍以已落库任务为准，并显示告警。提交接受、控制回执与恢复派发串行协调；迟到回执不得影响切换后的会话或清空新草稿。

本轮不自动解析任意含混任务关系，不把 Jev 分数作为执行授权。[固定业务评测](chat-intent-evaluation.md)区分规则边界、细分意图、历史回执重播和未验证语义；离线命中率不代表线上准确率。

相关验证入口：`tests/test_task_controls.py`、`tests/test_task_revision.py`、`tests/test_task_control_persistence.py`、`tests/test_chat_intent_evaluation.py`，以及前端 `chat-task-control.test.ts` 和 Chat/项目助手交互测试。
